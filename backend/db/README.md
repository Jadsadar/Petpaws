                                                          │ 1:N                │ N:1

**ความสัมพันธ์ที่ต้องสังเกต**

`conversations` อ้างถึง `pets` ด้วย **คีย์คู่** `(pet_id, owner_id)` ไม่ใช่แค่ `pet_id` เดี่ยว ๆ — อธิบายเหตุผลใน [กลุ่มที่ 4](#กลุ่มที่-4--แชท)

## กลุ่มที่ 1 — ผู้ใช้และการยืนยันตัวตน

### 1. `users`

บัญชีผู้ใช้ 1 คน

**สิ่งที่จงใจ "ไม่มี" ในตารางนี้: คอลัมน์ `role`**

SKILL.md เขียนไว้ชัดว่า

> ไม่มีการแบ่งบทบาทเป็น "ผู้ลงประกาศ" กับ "ผู้รับเลี้ยง" แยกกัน ทุกคนคือ user คนเดียวกันที่ทำได้ทั้งสองอย่าง

ถ้าใส่ `role` เข้าไป วันหนึ่งจะมีโค้ดที่เขียนว่า `if (user.role === 'owner')` แล้วกั้นไม่ให้เจ้าของปัดดูสัตว์คนอื่น ซึ่งผิดสเปค การไม่มีคอลัมน์นี้ทำให้เขียนแบบนั้นไม่ได้เลย

> **หมายเหตุ:** โค้ด Flutter ปัจจุบันมี `userRoles` อยู่ใน `mock_data.dart` (`'ฉันอยากหาหมาไปเลี้ยง (Adopter)'` / `'ฉันมีน้องหมาอยากหาบ้านให้ (Owner/Shelter)'`) ซึ่งขัดกับกฎข้อนี้ ต้องถอดออกตอนย้ายฝั่ง Flutter

**จุดที่ใช้ `citext` กับ email**

`citext` = ข้อความที่เปรียบเทียบแบบไม่สนตัวพิมพ์เล็กใหญ่ ถ้าใช้ `varchar` ธรรมดา `Somchai@mail.com` กับ `somchai@mail.com` จะสมัครเป็นคนละบัญชีได้ ซึ่งเป็นช่องทางสวมรอยที่เจอบ่อยมาก

**soft delete**

ลบบัญชีจริงไม่ได้ เพราะจะลากเอาประกาศ ข้อความ และห้องแชทของ **อีกฝ่าย** หายไปด้วย คนที่ไม่ได้ทำอะไรผิดจะเสียประวัติการคุยไปฟรี ๆ

### 2. `refresh_tokens`

**SKILL.md กำหนดว่า**

> ใช้ JWT access token อายุสั้น (15 นาที) คู่กับ refresh token อายุยาว (30 วัน) ที่หมุนเวียนทุกครั้งที่ใช้และ**เพิกถอนได้**

คำว่า "เพิกถอนได้" คือเหตุผลที่ต้องมีตารางนี้ JWT ที่ออกไปแล้วเพิกถอนไม่ได้โดยธรรมชาติ ถ้าไม่มีรายการฝั่ง server token ที่หลุดออกไปจะใช้ได้ต่อจนครบ 30 วัน โดยที่เจ้าของบัญชีทำอะไรไม่ได้เลยแม้จะรู้ตัวว่าโดนขโมย

**แนวคิด token family — ใช้ตรวจจับ token ที่ถูกขโมย**

ทุกครั้งที่ refresh ระบบจะออก token ใหม่และทำเครื่องหมายอันเก่าว่า `used_at` แล้ว token ทุกอันที่สืบทอดกันมาจากการล็อกอินครั้งเดียวกันจะแชร์ `family_id` เดียวกัน

```
ล็อกอิน  →  T1  →(refresh)→  T2  →(refresh)→  T3
            └─────── family_id เดียวกันทั้งสาย ───────┘
```

ถ้าจู่ ๆ มีคนเอา **T1 ที่ถูกใช้ไปแล้ว** มาใช้อีก มีคำอธิบายเดียวคือมีสำเนาหลุดออกไป ระบบจะเพิกถอนทั้ง family ทันที บังคับให้ทั้งขโมยและเจ้าของตัวจริงต้องล็อกอินใหม่ — เจ้าของจะรู้ตัวทันทีว่าเกิดอะไรขึ้น

**เก็บแฮช ไม่ใช่ token**

`token_hash char(64)` เก็บ sha256 หลักการเดียวกับรหัสผ่าน: ถ้าฐานข้อมูลหลุด คนที่ได้ไปจะสวมรอยไม่ได้

### 3. `password_reset_tokens`

รองรับหน้าจอ "ลืมรหัสผ่าน" ที่ SKILL.md ระบุไว้ในหน้าจอกลุ่มที่ 1

แยกจาก `refresh_tokens` เพราะคนละวงจรชีวิตและคนละความเสี่ยงโดยสิ้นเชิง — reset token ใช้ได้ครั้งเดียวและอายุสั้น (15–30 นาที) ส่วน refresh token อายุ 30 วันและหมุนเวียนได้ ถ้ายัดรวมตารางเดียวกันจะต้องมีคอลัมน์ `type` แล้วทุก query ต้องจำกรอง ซึ่งวันหนึ่งจะลืม

### 4. `device_tokens`

FCM token สำหรับ push notification (แผนข้อ 4)

**ทำไมต้องเป็นตารางแยก ไม่ใช่คอลัมน์บน `users`**

1 คนมีได้หลายเครื่อง — มือถือ แท็บเล็ต เว็บ ถ้าเก็บเป็นคอลัมน์เดียว การล็อกอินเครื่องที่สองจะเขียนทับเครื่องแรก แล้วเครื่องแรกจะไม่ได้รับแจ้งเตือนอีกเลยโดยไม่มีใครรู้สาเหตุ

**`unique` อยู่ที่ `token` อย่างเดียว ไม่ใช่ `(user_id, token)`**

เพราะเครื่องเดียวเปลี่ยนเจ้าของได้จริง — A ออกจากระบบ B ล็อกอินบนเครื่องเดิม ถ้า unique เป็นคู่ แถวของ A จะยังอยู่ แล้ว A จะได้รับแจ้งเตือนข้อความส่วนตัวของตัวเองเด้งขึ้นบนเครื่องที่ B กำลังใช้อยู่

## กลุ่มที่ 2 — ประกาศและสื่อ

### 5. `pets`

ประกาศหาบ้าน 1 รายการ — เป็นตารางหลักของทั้งระบบ

**กฎที่ schema บังคับ**

> SKILL.md: "Pet 1 ตัว มีเจ้าของได้คนเดียว (`pet.owner_id` เป็น field เดียว ไม่ใช่ตาราง join) — ห้ามทำ co-owner หรือ many-to-many"

`owner_id` เป็นคอลัมน์ `NOT NULL` ธรรมดา และจะไม่มีตาราง `pet_owners` โครงสร้างนี้ทำให้เขียน co-owner ไม่ได้เลยแม้จะเผลอ

**`age_months int` ไม่ใช่ `age varchar`**

โค้ดเดิมเก็บเป็นข้อความ `'2 ปี'` ซึ่ง:

- กรองช่วงอายุไม่ได้ (`WHERE age_months BETWEEN 0 AND 12` เขียนกับข้อความไม่ได้)
- เรียงลำดับแล้วได้ `'10 ปี'` มาก่อน `'2 ปี'` เพราะเรียงตามตัวอักษร
- ทำหลายภาษาไม่ได้

ยอมให้เป็น `NULL` ได้เพราะสัตว์จรมักไม่รู้อายุจริง — บังคับให้กรอกจะได้ข้อมูลมั่ว ๆ แทน

**`status` เป็น enum ไม่ใช่ข้อความไทย**

```
available → ยังไม่ถูกรับเลี้ยง    (แสดงใน deck)
pending   → กำลังคุยกันอยู่        (ไม่แสดงใน deck แต่ยังไม่จบ)
adopted   → ได้บ้านแล้ว           (หลุดจาก deck แต่ยังอยู่บนโปรไฟล์พร้อมป้าย)
```

โค้ดเดิมเก็บ `"ยังไม่ถูกรับเลี้ยง"` ตรง ๆ ปัญหาคือวันไหนแก้ข้อความที่แสดงผล ข้อมูลเก่าทั้งฐานจะหลุดจากเงื่อนไข query ทันทีโดยไม่มี error

**`UNIQUE (id, owner_id)` — index ที่ไม่ได้มีไว้ค้นหา**

ดูเผิน ๆ เหมือนซ้ำซ้อนเพราะ `id` เป็น primary key อยู่แล้ว แต่มีไว้ให้ `conversations` อ้างอิงแบบคู่ได้ อธิบายเต็มใน[กลุ่มที่ 4](#กลุ่มที่-4--แชท)

**`ON DELETE RESTRICT` ที่ `owner_id`**

ตั้งใจให้ลบ user ที่ยังมีประกาศอยู่ไม่ได้ บังคับให้ชั้น application ต้องจัดการประกาศก่อน แทนที่จะปล่อย `CASCADE` ลบประกาศหายไปพร้อมห้องแชทของคนอื่น

### 6. `pet_media`

รูป (และวิดีโอสั้นในอนาคต) ของสัตว์ 1 ตัว เรียงลำดับได้

**ทำไมชื่อ `pet_media` ไม่ใช่ `pet_photos`**

ตามแผนงาน: "สำหรับตอนนี้ทำแค่รูปก่อนหลังจากนี้จะสามารถอัพวิดีโอสั้นๆได้" — ถ้าตั้งชื่อ/ออกแบบตารางเป็น "รูปอย่างเดียว" ตั้งแต่แรก วันที่เพิ่มวิดีโอจะต้อง `RENAME TABLE` ที่มีข้อมูลจริงอยู่แล้ว ซึ่งเสี่ยงกว่าการเผื่อไว้ตอนที่ยังไม่มีข้อมูลมาก

คอลัมน์ `media_type` (`photo` / `video`) และ `duration_seconds` ถูกเพิ่มเข้ามาตั้งแต่ตอนนี้ แต่**เฟสแรกทุกแถวจะเป็น `photo` เท่านั้น** — ฝั่ง API จะยังไม่เปิดให้ส่ง `video` จนกว่าจะพร้อม ฐานข้อมูลรองรับไว้ล่วงหน้าเฉย ๆ

`duration_seconds` บังคับด้วย CHECK ว่ามีค่าเฉพาะตอน `media_type = 'video'` เท่านั้น และต้องไม่เกิน 60 วินาที (คลิปสั้นจริง ๆ ไม่ใช่วิดีโอยาว)

**ทำไมไม่เก็บเป็น array ของ URL บน `pets`**

1. ต้องเก็บ `storage_key` ไว้ลบไฟล์จริงบน S3 — ถ้าเก็บแค่ URL จะลบไฟล์ไม่เป็น
2. ต้องเก็บ `width`/`height` ไว้กัน layout กระโดดตอนโหลด
3. การ์ดใน deck ขอแค่สื่อชิ้นแรก แยกตารางแล้ว `LIMIT 1` ได้เลย ไม่ต้องดึงทั้งก้อน

> SKILL.md: "ส่งเฉพาะ field ที่หน้าจอใช้จริง การ์ดในเด็คไม่ต้องได้ description เต็ม ๆ กับรูปทั้ง 10 ใบ"

**`UNIQUE (pet_id, sort_order)`**

ห้ามมีสื่อ 2 ชิ้นลำดับเดียวกัน ไม่งั้นลำดับการแสดงผลจะสลับไปมาแบบสุ่มทุกครั้งที่ query

### 7. `media_uploads`

**ปัญหาที่ตารางนี้แก้**

การอัปโหลดแบบ presigned URL คือ client ยิงไฟล์ขึ้น S3 **ตรง ๆ** โดยไม่ผ่าน backend แปลว่า backend ไม่มีทางรู้ว่าไฟล์ขึ้นไปจริงหรือไม่

สถานการณ์ที่เกิดบ่อยมาก:

```
ผู้ใช้เลือกรูป → ระบบออก presigned URL → ไฟล์อัปขึ้น S3 สำเร็จ
   → ผู้ใช้กดปิดแอปก่อนกดโพสต์
   → ไฟล์ค้างบน S3 ตลอดกาล ไม่มีแถวไหนอ้างถึง ไม่มีใครรู้ว่ามันมีอยู่
   → แต่เสียเงินค่าเก็บทุกเดือน
```

ตารางนี้บันทึกทุกใบอนุญาตอัปโหลดที่ออกไป งานกวาดล้าง (BullMQ repeatable job) จะไล่ลบไฟล์ที่ `claimed_at IS NULL` และออกไปเกิน 24 ชั่วโมง

## กลุ่มที่ 4 — แชท

### 10. `conversations`

ห้องแชทระหว่างผู้สนใจกับเจ้าของ **เกี่ยวกับสัตว์ 1 ตัว**

> SKILL.md: "Conversation เกิดระหว่าง user 2 คน และอ้างอิง pet ที่เป็นต้นเรื่อง (`pet_id`) เพื่อให้เจ้าของรู้ว่าทักมาเรื่องสัตว์ตัวไหน"

คนคนเดียวกันทักเรื่องสัตว์ 2 ตัวของเจ้าของคนเดียวกัน = **2 ห้องแยกกัน**

#### `owner_id` ทำซ้ำมาจาก `pets.owner_id` — และวิธีกันข้อมูลเพี้ยน

SKILL.md บังคับ index `conversation(owner_id, last_message_at desc)` ซึ่งสร้างไม่ได้เลยถ้าไม่มีคอลัมน์ `owner_id` อยู่บนตารางนี้ จึงต้องทำซ้ำ

ปัญหาคลาสสิกของการทำซ้ำคือข้อมูลจะเพี้ยนเมื่อไหร่ก็ได้ ทางแก้ที่ใช้ที่นี่:

```sql
-- บน pets
CREATE UNIQUE INDEX pets_id_owner_id_key ON pets (id, owner_id);

-- บน conversations
FOREIGN KEY (pet_id, owner_id) REFERENCES pets(id, owner_id)
```

อ้างอิงทั้งคู่พร้อมกัน ผลคือ `owner_id` บนห้องแชท **เป็นไปไม่ได้เลย** ที่จะไม่ตรงกับเจ้าของจริงของสัตว์ตัวนั้น ต่อให้โค้ดฝั่ง NestJS เขียนผิด ฐานข้อมูลจะปฏิเสธเอง

ได้ความเร็วจากการ denormalize โดยไม่ต้องแลกกับความเสี่ยงข้อมูลไม่ตรงกัน

#### ตัวนับ unread อยู่บนห้อง ไม่ได้นับสดทุกครั้ง

endpoint `GET /conversations` ต้องคืน "รายการห้อง + unread count" ถ้านับสดด้วย `COUNT(*)` จะกลายเป็น 1 query ต่อ 1 ห้อง = **N+1** ซึ่ง checklist ของ SKILL.md ห้ามไว้ตรง ๆ

จึงเก็บ `initiator_unread_count` / `owner_unread_count` ไว้บนแถวห้อง และให้ trigger เป็นคนดูแล — การดึงกล่องข้อความจึงเป็น query เดียวจบ

#### `last_message_at NOT NULL`

ไม่ใช่แค่ความสะดวก แต่เป็นการบังคับกฎ: ห้องที่ไม่มีข้อความเลยต้องไม่มีอยู่จริง

### 11. `messages`

**`deleted_at` แต่ไม่ลบจริง**

ต้องเก็บตัวข้อความไว้แม้ผู้ส่งจะกดลบ เพราะถ้ามีการรายงานคุกคาม หลักฐานต้องยังอยู่ให้ตรวจสอบได้ ถ้าลบจริง คนคุกคามจะลบข้อความทิ้งแล้วปฏิเสธได้ทันที

CREATE INDEX messages_unread_idx ON messages (conversation_id, sender_id)

`WHERE read_at IS NULL` ทำให้ index มีขนาดเท่าจำนวนข้อความที่ยังไม่ได้อ่านเท่านั้น ซึ่งในระบบจริงน้อยมากเมื่อเทียบกับข้อความทั้งหมด — index 2,000 แถวแทนที่จะเป็น 2,000,000 แถว

## กลุ่มที่ 5 — การกำกับดูแล

### 12. `blocks`

**การบล็อกมีผลสองทางเสมอ**

เมื่อ A บล็อก B: สัตว์ของ B ไม่โผล่ใน deck ของ A **และ** สัตว์ของ A ไม่โผล่ใน deck ของ B

ถ้าทำทางเดียว คนที่บล็อกจะยังโดนคนที่ตัวเองบล็อกปัดเจอและทักมาได้อยู่ดี ซึ่งไม่ได้แก้ปัญหาอะไรเลย

**ใช้ composite primary key `(blocker_id, blocked_id)`**

คู่นี้คือตัวตนของแถวจริง ๆ ไม่มีเหตุผลให้มีคีย์สังเคราะห์ และได้ unique constraint มาฟรีในตัว

**`blocks_blocked_idx`**

primary key ครอบเฉพาะทิศ `blocker → blocked` จึงต้องมี index ย้อนกลับเพื่อตอบคำถาม "ใครบล็อกฉันไว้บ้าง" ซึ่ง query ของ deck ต้องใช้ทุกครั้ง

### 13. `reports`

รายงานได้ 3 อย่าง: ประกาศสัตว์ / ผู้ใช้ / ข้อความในแชท

**ทำไมไม่ใช้ `target_type` + `target_id` แบบ polymorphic**

รูปแบบ polymorphic ทำ foreign key ไม่ได้ ผลคือมีแถวที่ชี้ไปยัง id ที่ไม่มีอยู่จริงได้ตลอดเวลา และไม่มีอะไรมาจับ

ที่นี่ใช้คอลัมน์แยกที่เป็น FK จริงทั้ง 3 คอลัมน์ แล้วบังคับด้วย CHECK ว่าต้องมีค่าพอดี 1 อัน:

```sql
CHECK (
  (reported_pet_id IS NOT NULL)::int +
  (reported_user_id IS NOT NULL)::int +
  (reported_message_id IS NOT NULL)::int = 1
)
```

แลกความยืดหยุ่นบางส่วนกับการที่ฐานข้อมูลรับประกันความถูกต้องให้ ซึ่งคุ้มกว่ามาก

**ต้องใช้ partial unique index 3 อัน ไม่ใช่ unique ธรรมดา**

```sql
CREATE UNIQUE INDEX reports_unique_pet
  ON reports (reporter_id, reported_pet_id) WHERE reported_pet_id IS NOT NULL;
```

เพราะใน PostgreSQL ค่า `NULL` ไม่ถือว่าซ้ำกับ `NULL` — unique ธรรมดาบน 4 คอลัมน์จึงกันการรายงานซ้ำไม่ได้จริง

### 14. `provinces`

77 จังหวัดของไทย พร้อมภูมิภาคที่สังกัด (6 ภาค: กลาง/เหนือ/อีสาน/ตะวันออก/ตะวันตก/ใต้)

**ใช้ชื่อจังหวัดเป็น primary key ตรง ๆ ไม่สร้าง surrogate id**

`users.location` และ `pets.location` เก็บชื่อจังหวัดเป็น free text อยู่แล้ว (ตรงกับ `thaiProvinces` ในแอป Flutter) การ FK ไปที่ชื่อจึงไม่ต้อง migrate ข้อมูลเดิม แค่เพิ่ม constraint ทีหลังได้เลย

**ผลพลอยได้ที่ไม่ได้ตั้งใจแต่คุ้มมาก:** ก่อนหน้านี้ `location` เป็น `varchar(100)` อิสระ ใครพิมพ์ `"กรุงเทพ"` แทน `"กรุงเทพมหานคร"` จะหลุดจากทุก query ที่กรองด้วยจังหวัดแบบ exact match โดยไม่มี error เตือนเลย — พอมี FK แล้ว พิมพ์ผิดจะถูกปฏิเสธตั้งแต่ตอน insert

**migration มีการเช็กตัวเองว่าครบ 77 แถว**

```sql
DO $check$
BEGIN
  IF (SELECT count(*) FROM provinces) <> 77 THEN
    RAISE EXCEPTION 'provinces ต้องมี 77 แถว แต่พบ % แถว', (SELECT count(*) FROM provinces);
  END IF;
END $check$;
```

ป้องกันการพิมพ์ตกหรือคัดลอกซ้ำระหว่างก๊อปรายชื่อ 77 จังหวัดมาใส่ — ถ้าจำนวนไม่ตรง migration จะ fail ทันทีแทนที่จะปล่อยผ่านไปเงียบ ๆ

## `deck_feed` เวอร์ชันขยาย: กรองแท็ก + เรียงใกล้→ไกล

`deck_feed` ที่นิยามไว้ใน migration `008` (ย้ายมาจาก `007` เดิม เพื่อให้รันหลัง `provinces`/`traits` ถูกสร้าง) ขยาย 2 อย่างจากเวอร์ชันเดิม:

**1. กรองด้วยแท็ก — พารามิเตอร์ `p_trait_ids uuid[]`**

ตรงแท็กใดแท็กหนึ่งก็พอ (ANY match) ไม่ใช่ต้องมีครบทุกแท็กที่เลือก เพราะ "ต้องมีครบทุกแท็ก" (ALL match) จะทำให้ผลลัพธ์แคบเกินไปเร็วมากถ้าผู้ใช้เลือกหลายแท็กพร้อมกัน

**2. เรียงผลลัพธ์ใกล้→ไกล — คอลัมน์ `proximity_rank`**

`p_location` เดิมยังอยู่และทำหน้าที่เดิม (กรองเจาะจงจังหวัดเดียวแบบ all-or-nothing ถ้าผู้ใช้เลือกกรองเอง) ส่วนพฤติกรรม **ค่าเริ่มต้น** (ไม่ได้เลือกกรองจังหวัด) เปลี่ยนจาก "ไม่สนใจตำแหน่ง" เป็น "เรียงใกล้ก่อน":

```
rank 0 = จังหวัดเดียวกับผู้ดู
rank 1 = ภาคเดียวกัน (แต่คนละจังหวัด)
rank 2 = อื่น ๆ ทั้งหมด
```

**ทำไม keyset pagination ยังใช้ได้แม้ rank ไม่มี index รองรับ**

`proximity_rank` คำนวณสดจากการ join `provinces` ไม่ได้มาจาก index ตรง ๆ แต่คำนวณ **หลัง** ผ่านการกรองด้วย index ทุกตัวแล้ว (status, ไม่ใช่ของตัวเอง, ไม่เคยปัด, ไม่ถูกบล็อก) เซตที่เหลือให้เรียงจึงเล็กพอที่ Postgres sort ในหน่วยความจำได้เร็วโดยไม่ต้องมี index รองรับ — วัดจริงแล้วยังอยู่ที่ระดับหลัก ms ด้วยข้อมูลหลักพันประกาศ

เพราะทิศทางการเรียงผสมกัน (`rank` น้อยมาก่อน แต่ `created_at` ใหม่มาก่อน) การเทียบ cursor จึงเขียนเป็นเงื่อนไข `OR` แยกชั้น แทนการเทียบ tuple ตรง ๆ แบบเดิม:

```sql
WHERE proximity_rank > COALESCE(p_cursor_rank, 0)
   OR (proximity_rank = COALESCE(p_cursor_rank, 0) AND created_at < p_cursor_at)
   OR (proximity_rank = COALESCE(p_cursor_rank, 0) AND created_at = p_cursor_at AND id < p_cursor_id)
```

### กฎ "ห้องแชทเกิดพร้อมข้อความแรก" ทำงานยังไง

> SKILL.md: "การกดถูกใจต้อง **ไม่** สร้างห้องแชทอัตโนมัติ — ห้องแชทเกิดตอนผู้ใช้กดส่งข้อความแรกเท่านั้น"

ใช้ `CONSTRAINT TRIGGER` แบบ `DEFERRABLE INITIALLY DEFERRED` ซึ่งตรวจตอน `COMMIT` ไม่ใช่ตอน `INSERT`

```sql
-- ผ่าน
BEGIN;
  INSERT INTO conversations (...);
  INSERT INTO messages (...);
COMMIT;

-- ถูกปฏิเสธตอน COMMIT
BEGIN;
  INSERT INTO conversations (...);
COMMIT;   -- ERROR: ห้องแชท ... ไม่มีข้อความ
```

ผลคือ "ห้องแชทเปล่า" เกิดขึ้นในฐานข้อมูลนี้ไม่ได้เลย ไม่ว่าจะเขียนโค้ดพลาดยังไง

### ข้อจำกัดที่ต้องรู้

กลไก `docker-entrypoint-initdb.d` ทำงาน **ครั้งเดียวตอน volume ยังว่าง** เท่านั้น แก้ไฟล์ migration แล้วไม่มีผลจนกว่าจะ `down -v`

เหมาะกับ dev แต่ **ใช้บน production ไม่ได้** เพราะต้องล้างข้อมูลทิ้งทุกครั้ง production ต้องใช้ migration runner จริง (`node-pg-migrate`, Prisma Migrate หรือ TypeORM migrations) ที่จำได้ว่ารันอะไรไปแล้วบ้าง

### ORM: TypeORM (schema ยังมาจากไฟล์ SQL)

API ใช้ TypeORM แล้ว (`backend/api/src/database/`) แต่ไฟล์ SQL ในโฟลเดอร์นี้ยังเป็นแหล่งความจริงเดียว (single source of truth) ของ schema เพราะ schema ใช้ความสามารถที่ ORM ประกาศไม่ได้:

- partial index (`WHERE deleted_at IS NULL`)
- composite foreign key `(pet_id, owner_id)`
- `CONSTRAINT TRIGGER ... DEFERRABLE`
- CHECK constraint ที่ซับซ้อน
- ฟังก์ชัน plpgsql (`deck_feed`, `mark_conversation_read`, `message_preview` ฯลฯ)

กติกา:

- `synchronize: false` เสมอ ห้ามให้ TypeORM สร้าง/แก้ตารางเอง — เปลี่ยน schema ด้วย migration SQL ไฟล์ใหม่เท่านั้น
- entity (`src/database/entities/`) แค่อธิบายตารางที่มีอยู่ เพิ่ม/แก้คอลัมน์ใน migration แล้วต้องแก้ entity ให้ตรงกัน — `test/entities.e2e-spec.ts` จะล้มถ้าตารางจริงมีคอลัมน์ที่ entity ไม่มี
- คอลัมน์ที่ trigger/DB ดูแล (`like_count`, `*_unread_count`, `last_message_*`, `created_at`, `updated_at`) ประกาศ `insert: false, update: false` กัน `save()` เขียนค่าเก่าทับ
- query ที่ใช้ความสามารถเฉพาะของ Postgres (เรียก `deck_feed()`, CTE ของหน้ารายงานแอดมิน, `unnest`) เขียนเป็น SQL ผ่าน `dataSource.query` ได้ — เป็น connection pool เดียวกับของ TypeORM

### ความเร็วของ deck

ทดสอบด้วยข้อมูล **ผู้ใช้ 500 คน · ประกาศ 5,000 รายการ · ปัดไปแล้ว 2,000 ตัว**

**ก่อนเพิ่มฟีเจอร์หน้าค้นหา** (`deck_feed` เวอร์ชันแรก ไม่มี proximity ranking / trait filter):

```
Execution Time: 7.350 ms       ← เป้าหมายคือ < 100 ms
```

**หลังเพิ่มฟีเจอร์หน้าค้นหา** (`deck_feed` เวอร์ชันปัจจุบัน — join `provinces` 2 ครั้ง
เพื่อคำนวณ proximity_rank, เผื่อกรอง `pet_traits`) วัดซ้ำ 3 รอบต่อรูปแบบการเรียก
เพื่อตัดผลจาก cold-cache ของรอบแรก:

```
หน้าแรก (ไม่กรองแท็ก)        : 20.2 – 25.4 ms
หน้าแรก + กรองแท็ก (ANY match) : 18.0 – 23.7 ms
หน้าที่ 2 (มี cursor)          : 19.8 – 22.1 ms

→ นิ่งอยู่ในช่วง 18–25 ms ทุกรูปแบบ ยังต่ำกว่าเป้า 100 ms ราว 4–5 เท่า
```

ช้าลงจากเดิมประมาณ 3 เท่า (7ms → ~20ms) เพราะต้อง join `provinces` เพิ่ม 2 รอบ
(จังหวัดของ viewer + จังหวัดของแต่ละ pet) และ sort ทั้ง candidate set ด้วยค่า
`proximity_rank` ที่ไม่มี index รองรับโดยตรง — เป็นต้นทุนที่ยอมรับได้เพราะยังเหลือ
margin เยอะ ไม่ใช่สัญญาณว่าต้องรีบ optimize เพิ่ม

**บทเรียนสำคัญระหว่างพัฒนา:** ฟังก์ชันเวอร์ชันแรกที่เขียนด้วย `WITH` (CTE) เพื่อความ
อ่านง่าย วัดได้ไม่นิ่ง (เคยขึ้นสูงถึง 225ms ในบางรอบ) เพราะ `WITH` เป็น optimization
fence ที่ปิดกั้นไม่ให้ Postgres "inline" ฟังก์ชัน `LANGUAGE SQL` เข้ากับ query
ของผู้เรียก — พอเขียนใหม่เป็น flat `SELECT` เดียว (ไม่มี `WITH` เลย แลกกับต้อง
เขียน `CASE` คำนวณ proximity_rank ซ้ำ 5 ที่) ตัวเลขจึงนิ่งอยู่ในช่วง 18-25ms
ตามที่รายงานด้านบน ดู `db/migrations/008_deck_query.sql` สำหรับคำอธิบายเต็ม

แผนการ query ยืนยันว่าใช้ index จริง ไม่มี sequential scan บนตารางที่มีข้อมูลเยอะ และไม่มี N+1
(ยกเว้น `pets` เองซึ่ง sequential scan 5,000 แถวถูกกว่า index scan อยู่แล้วในสเกลนี้):

```
Seq Scan on pets (filter: status/deleted_at/owner_id/report_count) ← ยังเร็วเพราะข้อมูลพอดีหน่วยความจำ
Hash Anti Join กับ passes / likes                                  ← กรองตัวที่ปัดแล้ว
Memoize → Index Scan using users_pkey                               ← โหลดเจ้าของแบบ cache ไม่ loop
Memoize → Index Scan using provinces_pkey (x2)                      ← จังหวัดของ viewer และของแต่ละ pet
Index Scan using pet_media_pet_sort_key                             ← สื่อแรกของแต่ละตัว
```

### ข้อจำกัดที่เจอจากการวัด — ต้องรู้ไว้

**1. ยิ่งปัดเยอะ deck ยิ่งต้องไล่ index ลึกขึ้น**

ในแผนข้างบน Postgres ต้องไล่ index ไป **2,020 แถว** เพื่อหาให้ได้ 20 ใบที่ยังไม่เคยปัด เพราะ 2,000 ใบแรกถูกกรองออกหมด

ที่ 2,000 ยังเร็ว (7-20ms แล้วแต่เวอร์ชันฟังก์ชัน) แต่ถ้าผู้ใช้ปัดไป 50,000 ตัว จะช้าลงอย่างเห็นได้ชัด — ยิ่งชัดขึ้นไปอีกในเวอร์ชันปัจจุบันที่ต้อง sort ทั้ง candidate set ด้วย proximity_rank (ไม่ได้หยุดอ่าน index กลางทางเหมือนเวอร์ชันแรก)

ทางรับมือ (ทำเมื่อเริ่มเห็นอาการ ไม่ต้องทำตอนนี้):
- ใช้ cursor ต่อเนื่องภายใน session เดียว แทนที่จะเริ่มจากหน้าแรกทุกครั้ง
- ล้าง `passes` ที่เก่าเกิน 90 วันทิ้ง (ได้ผลสองเด้ง — deck เร็วขึ้น และการ์ดเก่าได้โอกาสอีกครั้ง)
- cache deck ที่คำนวณแล้วใน Redis ตามที่ SKILL.md กำหนดไว้อยู่แล้ว

**2. `likes` ใช้ seq scan ตอนตารางยังว่าง**

ในการวัดข้างบน ตาราง `likes` ไม่มีข้อมูลเลย Postgres จึงเลือก sequential scan ซึ่งถูกต้องแล้วสำหรับตารางว่าง เมื่อมีข้อมูลจริงจะเปลี่ยนไปใช้ `likes_user_pet_key` เอง

**3. proximity ranking ต้องคำนวณทุกแถวของ candidate set ก่อนเรียง**

ต่างจาก `created_at` ที่มี index รองรับให้ Postgres อ่านแล้วหยุดได้ทันทีที่ครบ `LIMIT` ค่า `proximity_rank` คำนวณสดจากการ join `provinces` จึงต้องกรองครบทุกเงื่อนไข (status, ไม่ใช่ของตัวเอง, ไม่เคยปัด, ไม่ถูกบล็อก, ไม่เคยรายงานเกิน 5 ครั้ง) จนเหลือ candidate set ก่อน ค่อย sort ทั้งก้อนในหน่วยความจำ — ที่ 5,000 ประกาศเหลือ candidate ~3,000 แถว ยัง sort ได้เร็ว (ส่วนหนึ่งของงบ 18-25ms) แต่ยิ่งฐานข้อมูลใหญ่ขึ้นเรื่อย ๆ candidate set ก็โตตาม ถ้าวันหนึ่งเห็นช้าลงชัดเจน ทางแก้ที่ตรงจุดที่สุดคือ cache ผล `deck_feed` ต่อผู้ใช้ไว้ใน Redis (ตามที่ SKILL.md กำหนดไว้อยู่แล้วเป็นข้อบังคับ ไม่ใช่ตัวเลือก) ไม่ใช่พยายามหา index มารองรับ proximity_rank ซึ่งเป็นค่าที่เปลี่ยนความหมายทุกครั้งที่ viewer เปลี่ยน จึงทำ index ตรง ๆ ไม่ได้อยู่แล้ว

### ข้อมูลตัวอย่าง

มี 3 ไฟล์ seed แยกกันตามโดเมนอีเมล ไม่ชนกัน รันพร้อมกันได้:

```bash
# ชุดหลัก — ใช้ตอนไล่ทดสอบ flow ทั่วไป (@petpaws.dev)
docker compose exec -T postgres psql -U petpaws -d petpaws -v ON_ERROR_STOP=1 < db/seeds/001_dev_seed.sql

# ชุดทดสอบ 10 บัญชี — ครอบคลุม edge case ที่ schema รองรับ (@petpaws.test)
docker compose exec -T postgres psql -U petpaws -d petpaws -v ON_ERROR_STOP=1 < db/seeds/002_test_accounts.sql

# ชุดสาธิต 10 บัญชี — "เปิดแอปแล้วใช้ได้เลย" ล็อกอินได้จริง (@petpaws.demo)
docker compose exec -T postgres psql -U petpaws -d petpaws -v ON_ERROR_STOP=1 < db/seeds/003_demo_accounts.sql
```

บน **PowerShell** ใช้ `<` ไม่ได้ ต้อง pipe เข้า `docker exec -i` แทน:

```powershell
Get-Content db\seeds\003_demo_accounts.sql -Raw -Encoding UTF8 | docker exec -i petpaws-postgres psql -U petpaws -d petpaws -v ON_ERROR_STOP=1
```

**`001_dev_seed.sql`**: ผู้ใช้ 4 คน · ประกาศ 5 รายการ (1 รายการเป็น `adopted`) · รูป 7 ใบ · แท็ก 9 · ห้องแชท 2 ห้อง · ข้อความ 4 ข้อความ

**`002_test_accounts.sql`**: ผู้ใช้ 10 คน · ประกาศ 9 รายการ · รายงาน 2 ครั้ง · บล็อก 1 คู่ — แต่ละบัญชีออกแบบมาให้ตรงกับ edge case เฉพาะข้อ ดูตารางในหัวไฟล์ว่าบัญชีไหนทดสอบอะไร (บัญชีถูกระงับต้องหายจาก deck ทุกคน, ประกาศ `adopted` ต้องหลุดจาก deck แต่ยังอยู่บนโปรไฟล์, บล็อกมีผลสองทาง, proximity rank ข้ามจังหวัดในภาคเดียวกัน ฯลฯ) — ทุกเคสรันจริงแล้วตรวจผ่านหมด

**`003_demo_accounts.sql`**: ผู้ใช้ 10 คน (ทุกคนมีประกาศของตัวเอง) · ประกาศ 13 รายการ (12 เปิดรับ + 1 `adopted`) · ถูกใจ 10 · ปัดผ่าน 4 · ห้องแชท 3 ห้อง · ข้อมูลติดต่อ+แท็กครบทุกบัญชี · กระจายครบทั้ง 6 ภาค

### Object storage (MinIO)

```bash
docker compose up -d minio
```

⚠️ **MinIO ถอด image ออกจาก Docker Hub แล้ว** (ย้าย distribution ไป quay.io ทั้งหมด) — `docker-compose.yml` ชี้ไปที่ `quay.io/minio/minio:latest` แล้ว ถ้าเผลอเปลี่ยนกลับเป็น `minio/minio` การ pull จะถูกปฏิเสธด้วย `pull access denied` (ยืนยันจากการทดสอบจริงตอนตั้งค่า ไม่ใช่ปัญหาเน็ตหรือสิทธิ์เครื่อง)

Console: `http://localhost:9001` (login ด้วย `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` ใน `.env`) — ยังไม่มี init script สร้าง bucket ให้อัตโนมัติ ต้องสร้างเองตอนเขียน media module (ROADMAP.md Phase 3.1)
